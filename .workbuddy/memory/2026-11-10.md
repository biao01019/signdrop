# 2026-11-10

## 项目：iOS 自签名工具（用户自己的 Apple ID 签名）

需求演进：先问"做牛蛙助手类自签名软件要准备什么" → 定为"用户用自己 Apple ID 自签"。

### 关键决策
- **放弃"一键登录"作为主路径**。苹果 GrandSlam/idmsa 接口是逆向所得，随苹果更新失效，
  改成两条路：手动证书模式（默认，稳定）+ Apple ID 一键模式（实验性，可关闭）。
- 不做 OTA 分发 / 不做云端签名服务：一旦对外就是"应用分发平台"，合规风险质变。
- 不做 7 天自动续签（需 iOS 端 WireGuard 环回，SideStore 那套，另一个量级）。

### 技术要点（复用价值高）
- `app/srp.py`：SRP-6a，RFC 5054 2048-bit 群（Apple 用这组），g=2，SHA-256。
  踩坑：素数常量手抄少 1 位导致 2044 位；1024/2048 群的 k 值不同
  （7556AA04… 是 1024 群的，2048 群是 A56303F3…）。已用 RFC 附录 B 的
  premaster secret 逐字节比对验证。RFC 原文：https://www.rfc-editor.org/rfc/rfc5054.txt
- `app/ipa.py`：重签三坑——① 必须清 `_CodeSignature`/`CodeResources`/`SC_Info`；
  ② 嵌套 `.appex`/Watch 的 Bundle ID 要以主包 ID 为前缀重写；③ Frameworks 的
  Info.plist 绝对不能动。
- `app/net.py`：苹果接口要 cookie 会话 + 读 409 响应体（2FA 信息），urllib 够用。
- 存储：SQLite + `data/secret.key`（Fernet）加密 p12 密码，避开系统钥匙串依赖。

### 结果
25 项测试通过（SRP 官方向量 / IPA 改写 / 端到端流水线）。服务 `python run.py`，
端口 8722，界面单页无构建。API 与服务均实测通过。

## 转折：用户要的是"能装进 iPhone 里直接用的 App"

电脑端网页工具不符合需求。改为交付 iOS 原生 App（`ios/`），PC 端降级为辅助。

### 两个物理约束（已向用户说明，后续沟通不必重复试探）
1. **工具本体必须先被外部装一次**：Xcode 直连（免费 ID，7 天）/ SideStore / 付费账号。
2. **App 内装别人的包必须走 VPN 环回**：`installd` 只收 USB 来源的安装请求。
   SideStore = minimuxer(Rust) + StosVPN(借已上架 App 的 WireGuard entitlement 建隧道)，
   因为免费 Apple ID 拿不到 Network Extension 权限。纯公开 API 做不到。

### iOS 端实现（从零写的签名引擎，不依赖 zsign）
- 架构：`SignKit`（SPM 本地包，纯 Swift，可测）+ `App`（SwiftUI）+ XcodeGen + GH Actions。
- `Support/ASN1.swift` DER 编码器（长度最短形式、SET OF 排序、INTEGER 补零）。
- `Signing/CodeDirectory.swift` CS_CodeDirectory v0x20400，头固定 88 字节；
  特殊槽编号按 cs_blobs.h：**-1 Info.plist / -2 Requirements / -5 Entitlements**（不是 -4）。
- `Signing/MachO.swift` **易错点：Mach-O 字段是小端，Apple 签名 blob 是大端**。
  第一次写成大端直接解析失败。签名分两步 `prepareSignatureSlot()` → `attachSignature()`，
  因为 codeLimit 就是签名区起点，而 CodeDirectory 又是被签名的内容。
- `Signing/CMS.swift` 手写 PKCS#7 SignedData + DER；签名后必须把 SET OF 的 0x31
  换成 [0] IMPLICIT 的 0xA0（内容不变、length 不重编码）。
- `Signing/Signer.swift` 流程：解压 → 扫描 → 前置校验 → 改 ID → 由内向外签名 → 重打包。

### 踩坑清单（每一条都会导致装不上或崩）
- 描述文件 `application-identifier` 带 Team 前缀（`TEAMID.com.x.*`），传入的 Bundle ID
  不带 → 前缀比较必须先剥 Team 前缀，否则通配符永远判 false。
- 裸 `.dylib` 的 infoPlist 是空字典，往里面塞 CFBundleIdentifier 会让它变非空，
  然后去给一个文件写 Info.plist → 必须提前 return。
- 原子写文件会把权限重置成 644，可执行位丢失 → 签完要显式 chmod 755。
- fat（通用）二进制必须报错而不是静默跳过，否则签了个没签的包。
- `INFOPLIST_KEY_*` 只在 `GENERATE_INFOPLIST_FILE: YES` 时生效，否则 Info.plist 缺失。

### 未完成 / 下一步
- CodeResources（资源封印）未生成，CodeDirectory 只有 -1/-2/-5 三个特殊槽。
  开发签名通常够用，报"签名无效"时优先补这个。
- App 内直接安装需接 minimuxer；当前路径是签完分享给 SideStore 装。
- 本机是 Windows，**Swift 代码未经编译验证**，靠 GH Actions 首次编译暴露问题。


## UI 1:1 复刻（设计稿 7 屏）

设计稿：`D:/系统文档/下载/Signdrop · iOS 自签名 App UI.pdf`（393×852）。
量化方法：PDF → PNG 150dpi（819×1776），K = 393/819；颜色用直方图取主色，
几何用 numpy + scipy.ndimage 连通域测卡片/图标/按钮，字号按字形中心间距反推。

### 两套产物，同一套数值
- `docs/ui/index.html`：7 屏 HTML 绝对定位复刻，用来迭代数值。
  收敛结果：与设计稿的差异像素占比 p1 3.75% / p2 3.99% / p3 3.42% /
  p4 4.49% / p5 4.60% / p6 4.28% / p7 2.93%，剩余基本是字体渲染差异
  （Windows 没有 PingFang）。
- `ios/App/Sources/`：同名数值移植到 SwiftUI（Theme / UIComponents / 7 个页面）。

### SwiftUI 结构
- `SignKitApp` 只注入 `AppModel`（内部持有 `AppState`，负责真实签名）。
- `RootView` = 登录门 + 四个 Tab + 三层全屏覆盖（详情 / 签名配置 / 导入证书）。
- 登录态存 UserDefaults `signdrop.signedIn`，登录页是首次启动的默认界面。
